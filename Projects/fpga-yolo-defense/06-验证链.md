# L5 验证链 · 组员共享版
> 用途：答辩被问"怎么证明你的结果是对的/软件硬件有没有算错"时用。这是全项目可信度的根基。

## 1. 第一性原理：验证 = 对照标准答案
没有标准答案就无法判断实现对错——"能跑通"≠"算得对"。芯片设计铁律：**先有参考模型（golden），再谈实现**，每级实现都向上对齐。你的项目把这条做到了极致：代码是**生成**的（model_graph.py 单一真值源 → gen_c.py 一键生成 C），杜绝手抄错误；每两级之间都有对拍。

## 2. 五级验证链（答辩必须能画/能背）
```
PyTorch 原模型（训练框架，最终锚点）
  │ ① float 金标 vs PyTorch：6 输出 max|diff| ≤ 1.4e-5
  ▼
float 金标 golden.py（与 PyTorch 语义 1:1）
  │ ② INT8 vs float：余弦相似度 obj 0.993 / cls 0.83–0.86 / reg 0.89–0.90
  ▼
numpy INT8 模拟 quantize.py
  │ ③ C(x86) vs numpy：输出 fin 逐字节相等
  ▼
C 代码 run_inference.c（gen_c 生成，x86 先验证）
  │ ④ 同一程序上 ARM 板：UART 输出串逐字符一致
  ▼
ARM 板上（Zynq PS）
  │ ⑤ 14 层换 PL：PL calls=22 errs=0，检测框与纯软件逐位一致
  ▼
PS+PL 协同（最终演示版）
```
一句话记忆：**PyTorch 锚底 → float 对齐（1e-5）→ INT8 对齐（余弦）→ C 对齐（逐字节）→ 板上对齐（逐字符）→ PL 对齐（逐框）**。

## 3. 答辩 30 秒表述
> "我们的可信度来自一条完整验证链：float 金标先和 PyTorch 原模型对拍到误差 1.4e-5；INT8 量化后与 float 余弦相似度 0.83–0.99；C 代码与 numpy 逐字节一致；同一程序上板后串口输出与 PC 逐字符一致。最后把 14 层搬到 PL，PL calls=22 errs=0、检测框不变——证明硬件加速没有改变结果。"

## 4. 曾经的 5 类 bug（"工程过程"叙事，主动讲加分）
早期 PS 版"能跑但检出 0 目标"，靠逐层对拍定位修复：
①量化数学错（溢出）②bias 被 int8 截断 ③ReLU 位置错 ④权重头两代混用/解码常数手填 ⑤输入预处理与训练不一致。→ 全部由"金标对拍"在几小时内定位到具体层。

## 5. 口径提醒
- ❌ 别说"在验证集跑了 500 张对比"——除非真有数据；诚实口径：板上单图实证 + 全链离线对拍。
- ❌ 别把四级说成"float 直接对比 PS"——每级都有独立中间产物（golden.py / quantize.py / gen_c）。
- "金标本身对吗？"→ 金标先对 PyTorch 对拍到 1.4e-5，锚定在训练框架。
- "cosine 为什么不到 1？"→ INT8 有损；obj 0.993 稳、cls/reg 略降，被后处理鲁棒吸收，最终框一致。
